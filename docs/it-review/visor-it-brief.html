A degree-planning and transfer-equivalency tool for Lipscomb advising, built as a scaled-up showcase of the Lunatic Labs student project. Today it holds fictional students only. This brief is for the IT review that has to happen before any real student record goes into it.

Not stored:

  • Uploaded transcript files. The file goes to Claude for that one read; the course list goes back to the browser and stays in the tab.
  • Signed-out chats.
  • Anyone's Anthropic key.

What is sent to Claude, and when

  • Ask Visor (chat). Each question and the text of earlier turns. Claude also has three read-only tools, which run on our server and send their results back to Claude:
    • the degree audit for the student in context: courses, grades, requirement status and the plan
    • the transfer-equivalency lookup
    • the course catalog
    Claude cannot change a plan. chat.py (TOOLS, _audit_digest)
  • Reading a transcript. The whole file (a PDF of up to 6 pages, or an image, up to 5 MB), so Claude can turn it into a course list. On the public site, only the bundled fictional transcripts can be read. Uploading a file is limited to advisors, registrars and admins. transcript.py, spec 08 US-8.3
  • Equivalency proposals. Public course titles and descriptions only, sent by a person running an offline batch job, never during a request. propose.py

Who can see what

  • The role always comes from our database, after the server checks the Clerk session token: its signature against Clerk's keys, the issuer, the expiry, and the site that requested it. A role claimed by the browser is ignored. Admins come from a server setting, VISOR_ADMIN_EMAILS; everyone else starts as a student. accounts.py
  • Saved chats can be read by the person themselves, the advisor assigned to that student, and admins. Students get a 403 on anyone else's. chat_log.py _can_read
  • Advisors can edit and approve plans only for their own advisees. Registrars decide equivalencies. spec 08 US-8.3
  • The log can't be edited: rows are only ever added, and each message carries a SHA-256 hash of the one before it, so a changed or missing message shows as a broken chain. spec 09, chat_log.py
  • Retention: a daily Vercel Cron job deletes a conversation, its messages and its read log 365 days after its last message. Only the cron secret or the server's write token can call it. chat_log.py purge, vercel.json

FERPA position today

The public site holds fictional students only. The repository is public, and everything under data/ is made up. The one real sample, an MTSU transcript, stays on a single Mac in a git-ignored folder. It was never committed or deployed, and it is used only for local tests. CLAUDE.md rule 4, spec 08, spec 09

Once real students use it, a saved chat about a student, and any transcript read for one, become part of the education record. That is the point at which this review is needed. Waiting on IT

Questions for IT

  1. May Visor hold real records at all: saved advising chats, and unofficial transcripts read by staff? If yes, which data classification applies, and what conditions come with it?
  2. Sending records to Anthropic. Does Lipscomb need its own agreement with Anthropic, such as a data-processing addendum or zero data retention? Should the key belong to a Lipscomb-owned account rather than mine?
  3. Sign-in. Should Visor use Lipscomb Microsoft sign-in, which would need an app registration from IT, or a production Clerk instance on a Lipscomb domain? Should lipscomb.edu addresses be the only ones allowed?
  4. Hosting and location. Are Vercel and Neon acceptable as processors? Which Neon region is required? (To confirm: the current Neon region.)
  5. Retention. Is one year right for saved chats? Who should hold the admin role, and who reviews the read log?
  6. Ownership. Who owns, runs and pays for it after the showcase (accounts, keys, the domain)?
