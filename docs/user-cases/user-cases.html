How we tested

Unit tests (117, all passing) prove the rules engine works piece by piece. These cases test it the way a person would: start from someone's goal, click through the real screens, and check every number on screen against the catalog data and the API's own answer.

AngleHow it was run
Student, advisor, registrarLocal app (React on Vite, Flask API, SQLite seeded from data/) driven in a real browser, desktop at 1280 px wide. A screenshot was taken for each case.
Ask VisorLive Claude Opus 5.5 through Visor's relay, using a server-side key so no key ever appears on screen. Every fact in each answer was checked against the catalog files.
Planner edge casesDirect calls to POST /api/audit. Every plan returned includes the independent checker's result (rules/verify.py), which shares no code with the planner.
GeneralLanding page, dark mode, and a 390 px phone viewport.

Verdicts: Pass worked as intended. Note worked, but we saw something worth improving. Fail did the wrong thing. Finding numbers (F1…) point to the last section.

Findings and recommendations

Ranked by how much each one matters to the people using Visor. Nothing was changed during testing; these are for the team to pick from.

HighF1 · Advisors can view plans but not change them

The original goal was an advisor who can view and modify a student’s plan. Today an advisor can open any plan, but there is no way to turn on summer, lower the load, move or pin a course, or approve the plan, although the landing page says advisors approve every plan. Next step: a short spec (06) for advisor overrides: plan settings, “pin this course to this term”, and an Approve button. Store the overrides, re-run the planner, and let verify() re-check the result so an override can never produce an invalid plan.

MediumF2 · The plan page hides transfer credit that doesn’t count

Pending, not-transferring and unknown courses are returned by the API but not shown. Add a “Transfer credit” card to the plan listing every course with its status pill, linking unknown ones to the Transfer tab.

MediumF3 · A graduation date is shown when courses couldn’t be placed

When there are unplaceable warnings, replace the date with “Can’t project yet: 5 courses not placed” and keep the date out of the advisee list.

MediumF4 · The same course can be flagged twice

Each click creates another pending review. Disable the button after a successful flag, and have the flag endpoint return the existing open review instead of adding one (the 409 path already exists for confirmed rows).

MediumF5 · Ask Visor stated a prerequisite without checking

The claim that CS 3433 depended on MA 3213 was wrong, because Casey’s MA 2314 already satisfies it. Either include each planned course’s prerequisites in the audit tool’s result, or add a line to the system prompt: call course_info before stating that one course depends on another.

LowF6 · Turning on summer can add terms without helping

Only open a summer term when it moves graduation earlier, and run the same last-term compaction with summer on.

LowF7 · Course code parsing on the Transfer tab

Require a letter subject followed by a number starting with a digit (^([A-Z]{2,5})\s*-?\s*(\d[\w]*)$), accept a hyphen, and clear the old result when showing an input error.

LowF8 · The audit API is too forgiving

Reject unknown grades with 400, return 400 for a missing program_id, and add a warning (and needs_review) for course codes not in the catalog.

LowF9 · Free-elective hours aren’t placed

When the last term is light, say “add 4 hours of free electives here” on that term instead of only in the footnote.

LowF10 · “Needed” on half-finished groups

Show a third state such as “Partly done” when some hours count but the group isn’t met.

LowF11 · Load line isn’t a real check

Compare checks.max_load with checks.load_limit and show a check or alert like the other lines.

LowF12 · No demo student shows the “needs review” path

Add a sixth fictional student whose plan produces a warning, so the advisor demo and the Needs review chip show something.

LowF13 · One demo equivalency is unlikely

CSCI 1020 (Object-Oriented Programming) is proposed as CS 2233 (Data Structures). That is fine as illustration, but a closer match makes a better demo.

New findings, 13 November

MediumN-F1 · Courses from schools Visor doesn't know can't be looked up

A transcript issued by MTSU lists its own courses without a known school, so Ask Visor can't check them. MTSU (8th on the registrar's list) is being added; a general fix is an "unknown school" row that a registrar can map.

LowN-F2 · Fictional test transcripts use old course numbers

Tennessee community colleges renumbered economics (ECON 2100/2200); the fictional transcripts still say ECON 2010/2020. Update them so demo lookups find the course.

LowN-F3 · Most of Claude's proposals are "elective"

Visor only knows the five majors' Lipscomb courses, so Claude often had no specific course to propose. Reading more of the Lipscomb catalog would turn many into specific matches.

LowN-F4 · Sign-in runs on Clerk's development instance

It shows a "development" badge and has usage limits. A production instance needs a custom domain; Lipscomb Microsoft sign-in needs an app registration from IT.

What held up well. Every plan we produced (five students, summer on and off, three credit caps) passed the independent checker with zero violations. Reasons on every course matched the catalog. Ask Visor refused to edit, used the planner’s own data, and named what it didn’t know.
